В GitLab Duo архитектура автоматизированного код-ревью (feature GitLab Duo Code Review) построена по модульному агентному пайплайну. Она объединяет события платформы GitLab, сервис-оркестратор (AI Gateway), контекстную сборку дифов и LLM с системными промптами.


Ниже представлена детальная логика работы агента от триггера до публикации комментариев в Merge Request (MR).


1. Триггеры запуска
   Агент активируется одним из двух способов:




Автоматически: через настройки проекта/MR (политика: автоматический запуск ревью при открытии MR или каждом push нового коммита).


По требованию (On-demand):




Пользователь вызывает команду/быстрое действие (quick action): /duo review.


Пользователь нажимает кнопку "Review with GitLab Duo" в веб-интерфейсе MR.


Упоминание @gitlab-duo review в треде комментариев.

2. Сбор контекста и препроцессинг (GitLab Rails Context Builder)
   Прежде чем отправлять данные в модель, система готовит контекст, чтобы минимизировать галлюцинации и уложиться в контекстное окно:




Анализ Diff (Unified Diff Parsing):




Извлекаются изменённые файлы (git diff target_branch...source_branch).


Отсекаются бинарные файлы, автогенерируемый код (lock-файлы, minified bundle) и файлы из списков исключений .gitlab/duo-ignore (или глобальных фильтров платформы).


Chunking & Budgeting:




Если диф превышает лимит токенов контекста, агент разбивает изменения на логические чанки (по файлам или смысловым блокам).


Вычисляется семантическая важность изменений: исходный код получает приоритет перед конфигами/документацией.


Обогащение метаданными (Project Context):




Заголовок и описание MR (чтобы понять намерение автора).


Язык программирования и расширения файлов.


Контекст окружения (существующие inline-комментарии, чтобы агент не дублировал замечания других ревьюеров).


Правила проекта (если подключены кастомные стандарты кодирования/rulesets).

3. Оркестрация запроса через AI Gateway
   GitLab отделяет логику платформы от непосредственного взаимодействия с нейросетями:


[ GitLab Instance (Rails / Gitaly) ]                │                ▼  (gRPC / mTLS)       [ GitLab AI Gateway ]    (Prompt Templates, Auth, Routing)                │                ▼  (API Call)        [ LLM Backend ] (Anthropic Claude / Vertex AI / Custom Model)


Security & Privacy Layer:




Проверка прав доступа пользователя и статуса подписки GitLab Duo (Enterprise/Pro).


Zero-Data Retention: данные дифа передаются провайдеру LLM с флагом запрета обучения на пользовательском коде.


Prompt Assembly (Сборка промпта):




Применяется системный промпт роли Senior Staff Engineer / Security Reviewer.


В тело промпта подставляются: правила форматирования ответов (JSON/Structured Output), исходные строки, смещения (diff line positions), описание задачи.

4. Алгоритм анализа в LLM (Аналитический цикл)
   Модель выполняет ревью по строгой многокритериальной воронке. Она оценивает код не просто как текст, а по конкретным инженерным срезам:


                  Входной Diff                        │      ┌─────────────────┼─────────────────┐      ▼                 ▼                 ▼ [Безопасность]   [Корректность]   [Производительность] (CWE, XSS,       (Логика, NPE,    (N+1, утечки, SQLi, Secrets)   Edge cases)      алгоритмы O(n))      └─────────────────┬─────────────────┘                        ▼             [Читаемость и стиль]             (Naming, Maintainability)                        │                        ▼           [Фильтрация ложных срабатываний]           (True Positive Check) 


Security & Vulnerabilities:




Поиск уязвимостей уровня OWASP Top 10 / CWE (SQL injection, XSS, небезопасная десериализация, hardcoded credentials).


Логическая корректность и Edge Cases:




Проверка условий, обработка null/undefined/nil.


Анализ гонок данных (race conditions), утечек памяти, незакрытых ресурсов (файловые дескрипторы, транзакции БД).


Производительность:




Поиск паттернов N+1 запросов к БД, неоптимальных циклов, избыточных аллокаций.


Readability & Best Practices:




Читаемость, архитектурная чистота, соблюдение идиом конкретного языка.

5. Постпроцессинг и валидация результатов
   Ответ модели не публикуется в «сыром» виде:




Mapping на координаты диффа (Hunk Matching):




Агент возвращает замечания с привязкой к конкретным строкам: old_line, new_line, file_path.


Парсер валидирует, что указанная строка действительно входит в изменённый диапазон (added или modified), а не является произвольным номером строки вне дифа.


Дедупликация и фильтрация шума:




Отсечение тривиальных замечаний (например, вкусовые правки форматирования, если в проекте уже есть linter/prettier).


Исключение комментариев, которые противоречат описанию задачи в MR.


Генерация предложений по коду (GitLab Suggestions):




Где возможно, замечание оформляется в виде синтаксиса suggestion:-0+0 ... , чтобы автор мог применить правку в один клик.

Архитектура Duo (и аналогичных ревью-агентов) использует гибридный подход: расширенный срез контекста вокруг изменений.

Почему «только diff» не работает
Если скормить модели только добавленные и удалённые строки:




Слепота типов и сигнатур: Вы изменили вызов функции getUser(id, withMeta). Без определения функции модель не знает, есть ли у неё второй аргумент, опциональный ли он и какой тип возвращает.


Ложные срабатывания (False Positives): Агент будет ругаться: «Здесь не объявлена переменная logger!», хотя она просто инициализирована выше по файлу вне зоны дифа.


Невидимость Breaking Changes: Изменение контракта в одном месте ломает вызовы в других, не затронутых дифом файлах.

Почему «весь проект целиком» не нужен


Ограничение контекстного окна: Даже при окнах в сотни тысяч токенов передача всей кодовой базы на каждый MR нерациональна по задержке (latency) и стоимости.


Проблема «иглы в стоге сена»: Чем больше лишнего кода в промпте, тем выше вероятность, что фокус модели размоется и она упустит неочевидный баг в 5 изменённых строках.

Как устроен баланс в GitLab Duo
Контекстный сборщик формирует многоуровневый пакет данных:


┌────────────────────────────────────────────────────────┐ │ 1. Unified Diff (Ядро: +/- строки)                     │ ├────────────────────────────────────────────────────────┤ │ 2. Context Windows (±30–50 строк вокруг изменений)     │ ├────────────────────────────────────────────────────────┤ │ 3. Whole-File Context (Полные файлы при малом объёме)  │ ├────────────────────────────────────────────────────────┤ │ 4. Repository Metadata (Сигнатуры, импорты, tree-sitter│ └────────────────────────────────────────────────────────┘


Ядро: Сам Unified Diff с добавленными, изменёнными и удалёнными строками.


Расширенный локальный контекст (Surrounding context): Включаются строки до и после изменённого блока (обычно от 20 до 100 строк вокруг каждого ханка, либо всё тело модифицируемой функции/класса).


Файловый контекст: Если изменённый файл относительно небольшой, он передаётся целиком, с разметкой того, какие именно строки были затронуты в MR.


Связанный контекст (Code Intelligence / RAG):




Заголовочные файлы, интерфейсы и импортируемые модули, на которые ссылается изменённый код.


Парсинг AST (через Tree-sitter / LSIF / SCIP), чтобы подтянуть точные сигнатуры вызываемых методов без чтения всего репозитория.


Метаданные MR: Название ветки, issue description, коммит-сообщения — чтобы понимать бизнес-логику изменений.

Итог: Агент работает по принципу «diff + локальное окружение изменений + интерфейсы зависимостей». Весь код проекта ему не нужен, но локальный контекст вокруг дифа обязателен.
